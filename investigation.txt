Atomic-add performance investigation (2026-09-27)

Question
--------
Why does the Linux Vulkan sweep fall to about 12.5 Gatomic/s at an 8 MiB
counter working set? The user reports that this happens even though the sweep
uses a 64 MiB counter buffer and backing allocation. That Linux result was
reported by the user; the measurements below were made on Windows.

Windows system and workload
---------------------------
NVIDIA GeForce RTX 4070; the sweep reported Vulkan driver NVIDIA 616.92.
Each dispatch performs 4096 workgroups x 256 threads x 1024 atomic adds =
1,073,741,824 adds. At the 8 MiB case, the shader addresses 2,097,152 u32
counter slots. All throughput values below are in Gatomic/s.

Results
-------
The investigate-branch single variant had a clear pass and checksum path; its
compiled shader matched the sweep shader byte for byte. Its continuous result
included clear time, whereas the sweep timed only its compute submission.

  Investigate branch, 8 MiB active range                 Throughput
  -----------------------------------------------------  ----------
  Sweep, 64 MiB buffer and backing allocation            31.846
  Single, 8 MiB buffer and backing allocation            ~12.4
  Single, 16 MiB buffer/allocation, 8 MiB active         ~12.5
  Single, 32 MiB buffer/allocation, 8 MiB active         ~12.5
  Single, 64 MiB buffer/allocation, 8 MiB active         ~32.9
  Single, 8 MiB buffer, 64 MiB backing allocation         32.9-33.1
  Sweep narrowed to 8 MiB buffer/allocation              12.048 median

The normal sweep figure was one sample from `--samples 1`, with validation
passed. For the narrowed sweep, both buffer exponents were temporarily set
to 23, giving only the 8 MiB case. Its three samples were 11.740, 12.048,
and 12.572; validation passed. Those temporary sweep edits were reverted.

On main, the single variant is simpler: it has no clear, checksum buffer,
uniform parameters, or readback. Its shader is different from the sweep
shader. The two main-branch runs below used the same shader, 8 MiB VkBuffer,
descriptor range, workgroup count, and five-second wall-time reporting loop.
Only the VkDeviceMemory allocation size changed.

  Main-branch simplified single variant                 Two report windows
  ----------------------------------------------------  ------------------
  8 MiB buffer and default (~8 MiB) allocation          12.414, 12.476
  8 MiB buffer and at least 64 MiB allocation           33.334, 33.507

Main-branch change
------------------
`vulkan_cpp_single/main.cpp` still creates an 8 MiB storage buffer and runs
the original dispatch-only command buffer. It now requests at least 64 MiB
for the VkDeviceMemory bound to that buffer, matching the sweep's backing
allocation on Windows. The shader, buffer usage, descriptor range, timing,
and lack of a clear pass are unchanged. The main-branch Release build ran
successfully and produced the two fast report windows shown above. The
single variant does not validate counters; these numbers measure submitted
atomic-add work divided by elapsed wall time.

deJong application observation
------------------------------
The user reports that C:\Development\deJong, the originating use case, remains
fast on Windows even with a 720-pixel texture (5.93 MiB counter buffer). That
720-pixel result was not measured in this session. Source inspection confirms
the buffer size formula is texture_size^2 * 3 * sizeof(u32); the three u32
counters per pixel receive three atomic adds per generated point. The shader
also evaluates trigonometric functions and follows a chaotic trajectory,
giving it a different address distribution from the microbenchmark's hashed
uniform random accesses. It clears the buffer each frame and uses GPU
timestamp queries for compute passes.

deJong's perf.txt records, at texture size 1440 (23.73 MiB buffer), Windows
Vulkan: 163.5 million points in 15.07 ms, and Linux Vulkan: 57.4 million
points in 15.25 ms, both on an RTX 4070. Those are point counts, not atomic
counts: multiplying by three gives approximate full-frame rates of 32.55
and 11.29 Gatomic/s respectively. The time includes more than the atomic
compute passes, so these are rough comparisons with the microbenchmark, but
their scale and Windows/Linux ratio are similar.

deJong creates the counter buffer through wgpu 29.0.1. In the locally installed
wgpu-hal 29.0.1 source, Vulkan buffers use gpu-allocator-managed allocation.
deJong requests the default device memory hints, Performance; wgpu-hal sets
minimum general memory block sizes of 128 MiB for device-only memory and
64 MiB for host-visible memory under that hint. Small buffers can therefore
be suballocated from a much larger VkDeviceMemory block. This is a plausible
reason why a 5.93 MiB wgpu buffer can be fast on Windows while a directly
allocated 8 MiB Vulkan buffer was slow. The actual memory type, block size,
and bind offset for deJong's buffer have not been captured, so this remains
an inference rather than a measured explanation.

Interpretation and Linux follow-up
----------------------------------
On this Windows machine, changing only the memory allocation size is enough
to move the simplified single variant from ~12.5 to ~33.4 Gatomic/s. The
earlier investigate-branch test found the same effect while keeping its
8 MiB VkBuffer and clear pass. The mechanism is unknown. In particular, the
Windows allocation change does not explain the user's Linux sweep result,
where a 64 MiB allocation is already slow at the 8 MiB working set.

Linux follow-up (2026-09-27)
----------------------------
On the RTX 4070 with Vulkan driver 615.71.09, the simplified single variant
was built in temporary directories with only the backing allocation size
changed. All runs used the same SPIR-V, 8 MiB VkBuffer and descriptor range,
and the same selected memory type (index 1, heap 0). The counter buffer's
VkMemoryRequirements were size 8,388,608 bytes, alignment 16 bytes, and
memoryTypeBits 31. Each run was stopped after two five-second wall-time
report windows; no GPU timestamps were captured.

  Backing allocation             First window   Second window
  -----------------------------  -------------  -------------
  8 MiB                          11.393         11.560
  64 MiB                         12.138         12.185
  128 MiB                        12.206         12.284

The 64 and 128 MiB allocations remain near 12 Gatomic/s on Linux. Thus, the
large-allocation change that lifted Windows from ~12.5 to ~33.4 Gatomic/s does
not reproduce on Linux. The smaller differences among these Linux runs may
reflect clock or background-load variation; they do not establish a useful
allocation-size effect. These tests did not inspect the supplied Nsight GPU
Trace files beyond their capture metadata.

Remaining work: compare GPU timestamps and performance counters across the
Windows and Linux single-variant runs. Capture deJong's actual VkBuffer size,
VkDeviceMemory allocation size, bind offset, selected memory type and heap,
and whether it shares a memory block. Keep the shader and workload fixed
within each comparison; deJong's three-channel chaotic workload is not
identical to the microbenchmark's one-channel random workload.

Nsight GPU Trace comparison (2026-09-27)

The user exported Summary and Metrics screenshots from the existing traces.
The Linux trace contains one submit and its Summary range is Entire Trace;
the Windows Summary range is Event Selection for one submit. Both Metrics
screenshots show GR Engine Active at 100%. These are GPU Trace measurements,
not the unprofiled five-second wall-time measurements above.

  Selected range                         Linux         Windows
  -------------------------------------  ------------  ------------
  Duration                               135.01 ms     42.64 ms
  L2 throughput / peak                   26.7%         85.8%
  SM throughput / peak                   1.9%          5.3%
  VRAM throughput / peak                 2.0%          0.7%
  VRAM read throughput / peak            1.6%          0.7%
  L2 bandwidth from L1TEX / peak        13.1%         40.9%
  L2 sector hit rate (all sources)       96.9%         99.5%
  L2 hit rate for L1TEX                  99.0%         100.0%
  Compute SM warp occupancy              37.3 warps    46.8 warps
  Compute SM warp occupancy / capacity   77.7%         97.4%
  Active threads per warp                32.0          32.0
  PCIe TX bandwidth                      3.0 GB/s      3.1 GB/s

The selected durations differ by 3.17x, close to the ratio of the unprofiled
throughput results, but the selected range types differ. The L2 throughput
ratio is 3.21x, while VRAM utilization is low in both traces. L2 traffic
from L1TEX tracks this ratio (3.12x), and L2 hits from L1TEX are reported as
99% or better on both systems. Windows drives L2 much harder; Linux does not
look limited by bulk VRAM bandwidth or pervasive L2 misses. The lower total
L2 hit rate on Linux may include non-shader sources and does not alone identify
the cause. The screenshots do not show L2 atomic counters or clock rates, so
they cannot yet identify the mechanism. The lower Linux occupancy is another
real difference, but its 1.25x ratio alone does not explain a 3x duration
difference.

The similar PCIe TX bandwidth over different durations yields about 407 MB
on Linux and 131 MB on Windows. GPU Trace sampling/profiling traffic is a
plausible source; this does not imply the counter buffer traverses PCIe.

The supplied Shader Pipelines CSV exports report the same 16 registers per
thread, zero shared memory, and 48-warp theoretical maximum on both systems.
Register pressure therefore does not explain the measured occupancy gap.
Nsight's average warp latency is 9.676 million GPU cycles on Linux versus
3.340 million on Windows (2.90x). The top stall reasons in both are Long
Scoreboard (LGSB) and LG Throttle (LGTHR), but their order reverses:

  Stall share among samples             Linux         Windows
  -----------------------------------   ------------  ------------
  Long Scoreboard                       52.6%         41.7%
  LG Throttle                           37.7%         49.4%

NVIDIA defines Long Scoreboard as waiting for a local/global/texture/surface
load dependency and LG Throttle as a full local/global memory instruction
input queue. This is consistent with Linux waiting longer for memory
operations and Windows feeding that queue more aggressively. It does not
prove whether the difference comes from generated instructions, memory
mapping, or another driver effect. The CSV exports have different shader
hashes and source-correlation metadata; the bytecode comparison below
resolves their shader-input equivalence.
The CSV header is shifted by one field near the stall columns; the stall
names and percentages above were read from the row values.

Next: compare L2 atomic metrics and GPU clock rates from the same submit
selections. Lower-level NVIDIA shader instruction views, if available, could
test whether the driver-generated atomic instructions differ.

Linux shader-frontend control
-----------------------------
The current CMake build prefers glslangValidator with -g; the earlier build
preferred glslc without debug information. On the same Linux system and
current source, both used an 8 MiB VkBuffer, 64 MiB backing allocation, and
the same dispatch. Two five-second wall-time windows from each:

  glslc:             11.286, 10.996 Gatomic/s
  glslangValidator:  11.769, 12.069 Gatomic/s

The frontend difference did not reproduce the Windows ~33 Gatomic/s rate
on Linux. The SPIR-V generated by the two frontends differs structurally
before optimization; the exported bytecode comparison below resolves the
question of equivalent shader input.

Exported shader bytecode comparison
-----------------------------------
Nsight exported windows-shader-bytecode.bin (2,040 bytes, Shaderc/Glslang)
and linux-shader-bytecode.bin (3,240 bytes, Glslang with embedded source
debug data). The Linux export exactly matches the SPIR-V in the local Linux
build by SHA-256. The Windows export differs from a locally compiled glslc
shader only in the ordering of two decoration pairs in its disassembly.

Running both exports through the same SPIRV-Tools `spirv-opt -O --strip-debug
--compact-ids` produced 1,120-byte modules whose only byte difference is the
SPIR-V generator ID in the header. Their executable instruction streams are
identical, including the loop, constants, hash, and OpAtomicIAdd. This
explains why the Nsight shader hashes differ without requiring a different
workload. The source frontends differ, but they deliver equivalent shader
logic to the NVIDIA driver.

The exact Windows-exported SPIR-V was copied into a temporary Linux build
without changing the C++ workload. Two five-second Linux windows measured
11.410 and 11.459 Gatomic/s with the 64 MiB backing allocation. Thus even
the byte-for-byte Windows shader input remains slow under Linux. A driver
backend code difference is still possible, as is a memory allocation or
mapping difference. Windows' separately measured 8 MiB versus 64 MiB
allocation effect demonstrates a memory-allocation dependence on that OS,
but does not by itself identify the Linux bottleneck.

Controlled Windows GPU Trace: 8 MiB versus 64 MiB backing allocation
--------------------------------------------------------------------
The user captured a slow Windows run after changing only
kCounterAllocationBytes from 64 MiB to 8 MiB and rebuilding with the old
glslc shader path. Nsight exported exactly the same 2,040-byte SPIR-V in
the slow and fast Windows traces (identical SHA-256), and the Shader
Pipelines rows have the same shader hash, 16 registers/thread, zero shared
memory, and 48-warp theoretical maximum. Both captures show one submit and
100% GR Engine Active in the selected range. The fast trace's Summary range
is Event Selection; the slow trace's is Entire Trace.

  Metric, one submit                         64 MiB fast   8 MiB slow
  -----------------------------------------  ------------  ------------
  Trace duration                             42.64 ms      125.66 ms
  L2 throughput / peak                       85.8%         27.7%
  L2 bandwidth from L1TEX / peak             40.9%         13.8%
  SM throughput / peak                       5.3%          1.8%
  VRAM throughput / peak                     0.7%          0.7%
  VRAM read throughput / peak                0.7%          0.7%
  L2 sector hit rate (all sources)           99.5%         98.7%
  L2 hit rate for L1TEX                     100.0%        100.0%
  Compute SM warp occupancy                  46.8 (97.4%)  46.2 (96.3%)
  Average warp latency                       3.340M cycles 9.766M cycles
  LG Throttle share of stall samples         49.4%         49.5%
  Long Scoreboard share of stall samples     41.7%         43.0%

The slow trace takes 2.95x longer, with 2.92x average warp latency and
about one-third the fast trace's L2 activity, despite virtually unchanged
occupancy and stall mix. It does not show increased VRAM bandwidth or a
large loss of L2 hits from the shader. Thus the 8 MiB allocation slows
the rate at which otherwise identical random atomic operations complete;
shader-input differences, register pressure, occupancy, and bulk VRAM
bandwidth do not explain the controlled Windows effect. A GPU address
translation/page-mapping or L2-atomic-path difference selected by allocation
size is plausible, but these counters do not measure either directly.

The slow Windows trace is also close to the Linux 64 MiB-allocation trace:
L2 throughput is 27.7% versus 26.7%, L2 from L1TEX is 13.8% versus 13.1%,
and average warp latency is 9.766M versus 9.676M cycles. Linux's measured
occupancy is lower (77.7% versus 96.3%) and its total L2 hit rate is lower
(96.9% versus 98.7%), but those differences did not prevent nearly the
same slow atomic rate. This strengthens a shared memory-system bottleneck
hypothesis. It does not prove that the OS drivers use the same mapping or
that allocation size has the same effect on Linux.

Most useful next test: keep an 8 MiB VkBuffer and 8 MiB allocation on
Windows, but vary only the shader's active SLOT_COUNT (for example 1, 2,
4, and 8 MiB) and record unprofiled throughput. The existing Linux sweep
with 64 MiB allocation stays near 32 Gatomic/s through about 1.2 MiB of
active counters, then declines to about 12.5 Gatomic/s by 8 MiB. The
Windows sweep with 64 MiB allocation stays near 33 Gatomic/s through about
16 MiB. If the Windows small-allocation curve has a knee near the Linux
one, that would further support an allocation-dependent address-mapping
or translation limit. It would still not directly measure GPU page size
or TLB misses.
